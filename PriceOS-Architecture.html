1. What PriceOS Does

PriceOS is an AI-powered revenue manager for property managers running short-term rentals (Airbnb / Booking.com / direct) in Dubai. It continuously answers the question every host loses sleep over: "What should I charge tonight — and for every night in the next few months — to make the most money without leaving the calendar empty?"

It does this by combining four kinds of intelligence and turning them into concrete, one-click price proposals:

  • Property intelligence — your calendar, occupancy, gap nights, and revenue forecast.
  • Booking intelligence — how fast you're selling, length-of-stay patterns, channel mix.
  • Market intelligence — competitor rates, demand "regime", festivals/events, and risk news (flight disruptions, advisories).
  • Pricing intelligence — a guard-railed engine that picks the revenue-maximising price and flags risky moves for human review.

A conversational agent named Aria ties it all together — the property manager simply chats: "How should I price next month to fill the calendar?" and gets a structured strategy with approve/reject proposal cards.

Who is this for?Property managers running 15–50 Dubai units who want institutional-grade revenue management without a dedicated revenue analyst on payroll.

4. The Agent Team

PriceOS uses a Manager–Worker pattern. Aria is the manager who talks to the user and decides who does what; seven specialist workers each own a narrow slice of intelligence.

👑 Aria Manager · Claude Haiku

The Chief Revenue Officer. Talks to the manager, reads precomputed analyses, delegates to workers, consolidates everything into one structured answer with proposal cards. Never prices on its own.

🏠 Property Analyst Claude Haiku

One property's calendar: occupancy, gap nights, LOS/min-stay recommendations, revenue forecast.

📈 Booking Intelligence Claude Haiku

Booking velocity, length-of-stay distribution, channel mix, day-of-week premium, ADR vs benchmark.

🌍 Market Research Claude Sonnet

Demand regime, competitor comp-set, validated events, source-market mix, guest sentiment.

🛡️ PriceGuard Claude Sonnet

The pricing optimizer. Picks the max-RevPAR price over an elasticity model and issues a guardrail verdict (approved / flag / hard-block).

🔍 Anomaly Detector Claude Sonnet

Post-execution monitor. Scores anomalies (velocity drops, price outliers, staleness) and recommends rollback on critical.

🗂️ Atlas Claude Sonnet

Portfolio view: cross-property revenue/occupancy comparisons, auto-flags under-performers.

📡 Event Intelligence Sonar Pro

Web sweep for events, holidays, geopolitics & risk news. Used as a fallback when SERP is rate-limited.
Developer note — why a Manager–Worker split? Each worker has a narrow prompt + a small toolset, so it stays accurate and cheap. Aria orchestrates and is the only agent that returns the user-facing cro_router_response schema. Workers return their own strict JSON schemas which Aria consolidates.

6. The Two Core Flows

Everything in PriceOS runs through one of two flows. Understanding this split is the key to the whole system.

🔥 Precompute (the "oven")

Triggered by Run Intelligence. Runs the 5 worker agents sequentially, each receiving raw DB data so it doesn't have to loop on tool calls. Results are cached for 4 hours.

POST /api/precompute-property

Property → Booking → Market → PriceGuard → Anomaly

💬 Live Chat (the "waiter")

Triggered by a chat message. Hits Aria, who reads the precompute cache (and live tools), then returns a consolidated answer with proposal cards. Fire-and-forget job, polled by the UI.

POST /api/chat

Aria → cache tools + delegation → structured JSON

8. Worked Example

Let's follow a real request end-to-end: the manager opens NH Luxury 1BR — Marina View, sets the date range Jun 7 – Jul 7, 2026, and types:

"Give me the pricing strategy for next month to fill all the gaps
 and increase occupancy."
1
Run Intelligence (data refresh)
The button fires runAllIntelligence() — in parallel it refreshes events (SERP Google Events + News + Ticketmaster, with date-verification), competitor rates (SERP/Airbtics comps), and guest sentiment. All land in MongoDB.
2
Precompute pipeline runs the 5 workers
The orchestrator pre-fetches raw data once (0 inventory rows, 2 reservations, 3 market events), then runs Property → Booking → Market → PriceGuard → Anomaly. Each gets the raw data + upstream outputs injected, returns strict JSON, and is cached.
3
Property Analyst output (cached)
Computes 25.8% occupancy, two confirmed reservations, a 3-night gap (Jun 12–14) and a 20-night gap (Jun 18–Jul 7), season = shoulder, floor = AED 502.
4
Market Research output (cached)
Reads SERP/Ticketmaster events with verified dates — Eid Al Adha (protected), Dubai Summer Surprises (+12%). Reads Airbtics comp-set (median ≈ AED 592). Flags risk-news if any.
5
PriceGuard output (cached)
Elasticity model is a stub → returns hold_for_review with a floor of AED 502 and a calibrated ceiling. No price is auto-applied; every proposal needs human sign-off.
6
Aria consolidates & answers
The chat message hits Aria with org_id, listing_id, dates, property_name + a fallback cache block. Aria reads the cache, surfaces PriceGuard's hold_for_review at the top, and builds a gap-fill strategy: protect Eid dates, relax LOS on the 3-night gap with up to 10% off, aggressive fill on the 20-night gap at ~AED 853.
7
UI renders proposal cards
Aria's cro_router_response JSON → the narrative becomes the chat bubble, and the proposals[] become Approve/Reject cards with current vs proposed price, verdict, and confidence.

SERP-primary, Event-Intelligence-fallback. SERP API is the primary source for events and risk news. If SERP hits a rate limit, the Lyzr Event Intelligence agent runs a verified web sweep instead — so the system degrades gracefully rather than going blind.

10. Guardrails & Safety

  • Human-in-the-loop pricing. No price is pushed live automatically. Every proposal is hold_for_review / flag_review / approved and surfaced as an Approve/Reject card.
  • Price floor & ceiling. Proposals never go below the configured floor (e.g. AED 502) or above the calibrated ceiling.
  • Protected event dates. LOS/price are locked on high-confidence events (e.g. Eid).
  • No fabrication. Agents are instructed to never invent occupancy, comps, regime, or event numbers — if a value is unavailable, they say so and record it in data_warnings.
  • Date verification. Festival/holiday dates are validated against a known UAE calendar before they reach pricing.
  • Anomaly monitoring. Post-execution checks (velocity drop, price outlier, staleness) recommend rollback on critical severity.

Structured output contract

Every agent enforces a strict JSON schema via Lyzr's response_format. Aria returns cro_router_response:

{
  "intent": "pricing_decision",
  "answered_directly": false,
  "agents_consulted": ["PropertyAnalyst","MarketResearch","PriceGuard"],
  "narrative": "…markdown the user sees…",
  "proposals": [{ "proposal_id","date","current_price","proposed_price",
                  "change_pct","guard_verdict","expected_revpar","rationale" }],
  "action_buttons": ["approve","reject"],
  "escalations": [],
  "audit_decision_id": ""
}
Why Aria gets a "fallback cache block". A Lyzr manager agent tends to delegate rather than call its own attached tools. To guarantee correct numbers, the chat route reads AgentCache server-side and injects it as a fallback block — Aria prefers a live tool call, but always has the precomputed values to fall back on. This prevents the "0% occupancy / data unavailable" failure mode.
Known operational gotchas
  • ngrok URL must point at the running dev server (port 3000) or every tool call 404s. Update the servers[0].url in the OpenAPI specs when ngrok restarts.
  • Tool registration — a ⚠️ on a tool in Lyzr Studio means the name exists but the OpenAPI schema isn't registered; re-add via + Add → OpenAPI Schema.
  • Model drift — agent models can revert when edited in Studio; re-pin after UI saves.
  • Cache TTL is 4h — cache readers return 404 CACHE_MISS when cold; click Run Intelligence to warm it.
