PriceOS Agent Dossier

Every PriceOS Agent, what it owns, what it calls, and where human approval still matters.

PriceOS is not one monolithic AI assistant. It is a layered operating model: a portfolio guide for dashboards, a revenue orchestrator for pricing conversations, specialist workers for analysis, setup agents that seed market intelligence, guest communication agents for inbox operations, and hard-control agents that verify or execute only after approval. This page is designed to explain that structure in plain English while staying faithful to the repo's prompts, route handlers, and tool specs.

How The Agent Layer Works

Operating model from question to action

The cleanest way to explain PriceOS to a client is to show that analysis and execution are intentionally separated. Some agents advise. Some classify. Some enrich context. Only one execution layer pushes approved changes to the PMS.

1

Context is assembled first

Portfolio, listing, inventory, reservation, event, benchmark, and guest-thread context are loaded either from injected system context, internal database reads, or approved tool calls. Atlas uses injected portfolio context only. Aria can operate from context first and, in the tool-led prompt design, fetch property data through agent tools when a fresh property analysis is needed.

Dashboard: zero tools Property chat: context + property tools Guest inbox: thread and reply tools
2

Specialists analyse one narrow problem at a time

PriceOS splits responsibilities on purpose. Booking Intelligence explains bookings and revenue. Property Analyst optimises open dates. Benchmark compares against competitors. Market Research explains events and seasonality. PriceGuard classifies risk. This means each agent stays narrow, auditable, and easier to explain.

No single agent owns everything Each worker has a narrow mandate Safety is layered, not implied
3

Recommendations are reviewed before anything is pushed live

PriceGuard decides whether a proposed price change is routine, review-worthy, or risky. Guardrails then enforce the hard floor, ceiling, and daily-change boundaries. Approved items can move to the Pricing section, but that still does not mean the PMS has been updated yet.

Classification layer Hard-clamp layer Human confirmation layer
4

Only the execution layer writes out to the PMS

The Channel Sync Agent is the controlled executor. It accepts only approved proposals, writes the change to the PMS, reads it back to verify success, logs the result, and can trigger rollback if the write fails or verifies incorrectly.

Write only after approval Verification read-back required Rollback supported

Core Revenue Agents

The two user-facing intelligence layers

Atlas speaks for the portfolio. Aria speaks for the property-level revenue conversation. They feel similar in the UI, but they are intentionally different in data scope and responsibility.

Atlas

Dashboard Agent and portfolio assistant

Portfolio Intelligence
Prompt-defined Dashboard chat No tools allowed
What Atlas is responsible for

Portfolio overviews, top and bottom performers, revenue breakdowns, cancellation analysis, channel concentration, market-event awareness, and dashboard-level action prompts for the operator.

What Atlas reads

Injected [SYSTEM CONTEXT] only. The documented context includes portfolio properties, reservation summary, revenue by channel, recent bookings, recent cancellations, and upcoming events.

Tool calls

None. Atlas is explicitly instructed to make zero tool calls and to answer only from the provided context block.

Outputs

A structured dashboard response with portfolio summary, system health, alerts, and a markdown chat answer.

What Atlas never does

It never fetches tools, never exposes raw JSON, never reveals IDs or keys, and never pushes any live change.

Aria

CRO Router and conversational revenue manager

Revenue Orchestrator
Prompt-defined Agent Chat Action buttons flow
What Aria is responsible for

Interpreting pricing questions, understanding the listing and date range, gathering the right data, routing to specialist analysts, combining the outputs, and returning a client-readable pricing recommendation.

What Aria reads

In the prompt-library design, Aria can use property tools. In the architecture reference, Aria can also answer from a fully assembled property context built from listing details, inventory, reservations, pricing rules, events, and cached Airbtics pacing.

Tool calls documented for Aria

get_property_profile, get_property_calendar_metrics, get_property_reservations, get_property_market_events, and get_property_benchmark.

Outputs

Routing metadata, pricing proposals, risk and comparison context, and a long-form markdown answer that the chat panel can render.

What Aria never does

Aria does not directly push pricing to the PMS. It also should not invent numbers or bypass PriceGuard, Guardrails, or human review.

Pricing Specialists

The worker agents that break pricing into explainable parts

These are the focused workers Aria can rely on or that the pricing pipeline conceptually mirrors. Each one handles a different slice of the pricing problem so the client can see why a recommendation exists.

Property Analyst

Also described as the Pricing Optimizer

Calendar Proposal Engine
Prompt library Gap-night logic
Responsibility

Find available nights, apply pricing rules in priority order, add event uplift, clamp to floor and ceiling, and write proposal reasoning per date.

Inputs

inventory, pricing_rules, market_events, property, and occupancy metrics.

Calculations it owns

changePct = ((proposedPrice - currentPrice) / currentPrice) * 100, plus summary counts such as pending vs auto-approved proposals.

What it never does

It never edits booked or blocked nights and never writes live prices to channels.

Booking Intelligence

Revenue, occupancy, LOS, and channel mix specialist

Booking Analyst
Prompt library Reservations focus
Responsibility

Explain revenue, occupancy, ADR, RevPAN, upcoming arrivals, average length of stay, and booking channel mix from the bookings already on hand.

Inputs

active_bookings and metrics passed in by the orchestrator or pipeline.

Calculations it owns

ADR, RevPAN, channel aggregation, occupancy from booked vs bookable days, and arrival sorting.

What it never does

It never invents missing demand data and never proposes live price pushes by itself.

PriceGuard

Adjustment Reviewer and risk classifier

Proposal Risk Layer
Prompt library UI references present
Responsibility

Review proposal magnitude, detect guardrail breaches, downgrade or upgrade risk based on event justification, and decide which changes should appear for approval.

Inputs

Proposed prices in inventory, floor and ceiling bounds, occupancy context, and event overlap.

Risk logic

Micro adjustments can auto-approve; moderate and high changes are escalated; event-backed spikes can be justified but still surfaced.

What it never does

It does not push prices, does not erase safe auto-approved changes, and does not replace the hard clamp layer.

Gap & LOS Optimizer

Minimum-stay and gap-fill specialist

Restriction Optimizer
Prompt library LOS proposals
Responsibility

Find unbookable gaps, recommend temporary minimum-stay reductions, and optionally pair them with urgency-based discounts for last-minute fill.

Inputs

Calendar data, reservation spacing, seasonal patterns, days-to-arrival, floor and ceiling bounds, and minimum-stay limits.

Outputs

gap_fill and los_calibration proposals with urgency, proposed minimum stay, optional price discount, and human-readable reasoning.

What it never does

It never pushes LOS changes directly to Hostaway and never alters booked dates.

Market and Setup Agents

The agents that enrich the property before day-to-day pricing happens

PriceOS uses a setup-time intelligence pass to bring in competitor context, events, holidays, news, and initial price boundaries. This is the part a client can think of as the platform's market onboarding brain.

Marketing Agent

Documented both as event research and as gap-fill messaging support

Demand Narrative Layer
Run Aria setup Prompt library Events + copy
Responsibility

In setup mode, it turns city, date range, Airbtics pacing, and seasonal context into a structured events, holidays, and demand narrative. In runtime prompt form, it also suggests promotional copy, listing improvements, and channel-specific messaging to fill calendar gaps.

Trigger

POST /api/market-setup according to the agent-call reference, plus promotional support in marketing-oriented prompt flows.

Inputs and APIs behind it

City, area, dates, Airbtics pacing snapshot, plus event feeds such as Eventbrite, Ticketmaster, DTCM, and RSS data synced beforehand.

Writes and outputs

Structured market-event payloads, demand outlook, and in the setup flow, saved market-event intelligence in Mongo-backed collections.

Benchmark Agent

Competitor Scanner and market-positioning layer

Competitive Positioning
Run Aria setup Benchmark route exists
Responsibility

Place the listing on a percentile curve, compare it to the comp set, and recommend target weekday, weekend, and event rates.

Trigger

POST /api/market-setup in the documented setup flow, plus runtime benchmark reads when Aria or the UI asks how the listing compares.

Inputs

City, area, bedrooms, base price, date range, and Airbtics ADR percentiles such as P25, P50, P75, and P90.

Writes and outputs

Positioning verdict, percentile context, recommended rates, comp examples, and BenchmarkData records used later in UI widgets and analysis.

Market Research

Runtime explainer for events, seasonality, and external demand signals

Event Impact Interpreter
Prompt library Market explanations
Responsibility

Translate market events into practical pricing guidance and area-level impact. If there is no event, explain the seasonal baseline rather than inventing a spike.

Inputs

market_events at runtime, plus the property's area and current base price so it can convert uplift percentages into actual currency values.

Outputs

Event windows, impact tiers, recommended prices, seasonal commentary, and a top recommendation for the property manager.

What it never does

It never fabricates missing events and never writes the PMS price itself.

Guardrails Agent

Silent hard-boundary enforcer

Safety Clamp Layer
Setup and pipeline safety Hard limits
Responsibility

Enforce the absolute floor and ceiling, clamp out-of-bounds proposals, escalate excessive single-day changes, and write warning insights when a clamp occurs.

Trigger

The setup docs show a conditional first-run role when floor and ceiling are empty. The prompt library also defines a background validation pass after proposals are generated.

Writes and outputs

Adjusted proposal values, guardrail flags, updated change percentages, and warning insights for the dashboard or logs.

What it never does

It never suppresses valid safe changes and never acts as the final human approver.

Guest Communication Agents

Two separate guest-intelligence jobs: reply now, summarise later

The guest layer is intentionally split. One agent behaves like a live operations responder. The other behaves like an analyst that condenses inbox patterns for the property manager.

Guest Reply Agent

Also called Reservation Agent or Chat Response Agent in different docs

Live Guest Ops
Guest Inbox draft route Webhook auto-reply path Hospitality tone
Responsibility

Read the guest's message, identify intent and sentiment, answer normal operational questions, create operations tickets when something is broken, escalate risky cases, and send access details through the proper secure path instead of free-text guessing.

Current live routes

POST /api/hostaway/suggest-reply drafts replies in the background. The Hostaway webhook route can also trigger the guest agent automatically when live mode is enabled.

Documented action tools

read_thread, send_reply, create_ops_ticket, escalate_thread, send_access_details, and close_thread.

Current route prompt behaviour

The live draft route explicitly asks the Lyzr agent to read thread context and then choose the correct action path, including guest messaging, ticket creation, escalation, access sharing, property-data lookup, or upsell support.

What it never does

It must not invent entry codes, offer refunds, reveal owner notes, or ignore manual-review states like paused or approval-required communication settings.

Conversation Summary Agent

Guest insight summariser for trends and actions

Inbox Intelligence
Per-thread summary route Prompt library
Responsibility

Read a conversation set or thread, judge overall sentiment, identify repeating themes, count unresolved replies, and give the property manager concrete action items.

Current live route

POST /api/guest-agent/threads/[id]/summary loads the conversation, calls the Lyzr summary agent, and returns sentiment, themes, action items, and bullet points.

Documented tool model

The session-init and prompt docs also describe a direct tool-driven version using get_guest_conversations for listing-wide summary generation.

Outputs

Sentiment badge, recurring themes, action list, bullet summaries, total conversation count, and needsReplyCount.

What it never does

It never sends replies to guests and never includes contact details or internal identifiers in the summary.

Guest communication approval boundary

One important client-facing point is that reply intelligence and live sending are different. The current repo includes draft generation, webhook-triggered reply logic, and a save-reply route that stores admin replies into MongoDB. That means the guest layer can assist heavily, but approval or live-send policy is still controllable through communication state and webhook settings.

Execution and Control

The layers that make automation safe enough to explain confidently

These agents exist so the client can trust that analysis does not automatically mean uncontrolled action. One writes only after approval. One watches for unintended consequences.

Channel Sync Agent

The controlled PMS write layer

Execution Agent
TypeScript class exists Push-after-approval
Responsibility

Take already approved proposals, write them to the PMS calendar, verify the write by reading back the calendar, update database state, log the batch, and rollback failed dates if needed.

Trigger

Only after CRO-authorised approval and only for proposals whose verdict is approved. The documented session payload explicitly includes cro_authorization: true.

System calls it makes

PMS API write, PMS API read-back, and MongoDB writes to execution logs and inventory state.

What it writes

Approved current prices, sync timestamps, batch-level execution results, and failure states such as sync_failed.

What it never does

It never pushes unapproved pricing, never ignores stale-data checks, and never hides a failed verification.

Anomaly Detector

Post-change watchdog and rollback recommender

Monitoring Agent
Prompt-defined Score-based monitoring
Responsibility

Detect booking velocity collapse, price outliers, data staleness, repeated execution failures, price cliffs between adjacent dates, and damaging revenue impact after a change.

Trigger

Full analysis requests, explicit anomaly checks, daily sweeps, and documented post-sync monitoring windows such as 30 minutes after a Channel Sync execution.

Inputs

Price change history, before/after booking snapshots, comp-set ADR, last sync timestamp, calendar metrics, reservations, and benchmark context passed in by the orchestrator.

Outputs

Anomaly score, severity tier, actions recommended, rollback recommendation, and autopilot-pause recommendation.

What it never does

It does not modify prices directly and does not write to the PMS. It advises the orchestrator and operator on whether a rollback should happen.

Client Talking Points

The simplest way to explain the agent model to a client

If this needs to be presented in a meeting, these are the messages that make the architecture feel trustworthy and understandable.

1. PriceOS separates advice from execution

Most agents are analytical. They explain, compare, score, summarise, or recommend. Only the Channel Sync layer is allowed to write pricing into the PMS, and only after approval.

2. Every agent is scoped

Atlas does portfolio health. Aria orchestrates property analysis. Guest Reply handles guest operations. Summary looks for guest trends. Narrow mandates make behaviour easier to audit and explain.

3. Safety is layered, not assumed

PriceGuard reviews proposal risk. Guardrails enforce absolute pricing bounds. Human approval still sits between analysis and live channel updates.

4. Market context is not guesswork

Setup agents use benchmark data, Airbtics context, and synced event sources so that price recommendations are grounded in market conditions rather than generic AI text.

5. Guest communication has clear escalation paths

The guest agent can answer normal hospitality questions, but maintenance, legal, refund, or injury issues are escalated instead of being improvised.

6. Monitoring continues after a change

Once prices are pushed, the anomaly layer can still watch for harmful outcomes like booking collapse, stale syncs, or suspicious price cliffs.

Source Notes

What this page was compiled from

This guide was written from the repo's current prompt files, architecture notes, OpenAPI tool specs, and live guest-inbox route handlers. Where the repo contains two documented operating modes, this page calls that out instead of hiding it.

Important nuance: some prompt files describe a more tool-driven orchestration model, while the current architecture reference also documents a full-context chat path where the CRO can answer from a pre-built context payload. That is not a contradiction in product story terms: it means PriceOS is designed to support both preassembled context and controlled live fetches depending on the flow.
