# Data Layer Specification

## What changed

Three new core tables (`agent_decisions`, `state_snapshots`, `decision_outcomes`) plus supporting tables for posteriors, regime states, clusters, segment profiles, comps, events, RM actions, evaluation runs, and guest signals. Full SQL is in `/schemas/audit-schema.sql`.

Every Lyzr agent invocation logs to `agent_decisions`. Every input state at decision time is captured in `state_snapshots`. Every booking outcome is captured in `decision_outcomes` when the night passes.

## Why

Resolves shortcomings:
- 2 (stateless sub-agents): the audit log gives every agent persistent memory that survives sessions
- 14 (no audit-and-replay): the snapshot table reconstructs decision-time state for replay
- 17 (no internal ground truth): outcomes tie back to predictions for calibration measurement
- 20 (veto as workaround): JSON outputs in `agent_decisions.outputs` enable schema validation as the single source of truth

## Impact on product

- Backtest 24 months of Hostaway data overnight
- Replay any decision with new prompt or constants and see counterfactual
- Customer audit rights become enforceable (prior turn's performance contract clause)
- Calibration error becomes a measurable, ship-blocking metric
- RM corrections feed back as labeled training data

## Snapshotter service

The snapshotter assembles and writes a `state_snapshots` row before each decision. Inputs come from PMS, comp store, regime classifier, event store.

```python
# pseudocode
def snapshot_state(property_id: UUID, ts: datetime) -> UUID:
    snapshot_id = uuid4()
    state = {
        "calendar":          pms.get_calendar(property_id, days=365),
        "reservations":      pms.get_reservations(property_id, days=365),
        "comp_set":           comps.get_state(property_id, ts),
        "events":             events.get_validated(property.city,
                                                   window=(ts, ts+365)),
        "news":               news.get_recent(property.city, days=30),
        "market_context":     {
            "regime":            regime.classify(property.city, ts),
            "currency":          fx.get(property.currency_pair),
            "weekend_def":       cluster.weekend_def_for(property.cluster_id)
        },
        "guardrails":         strategy_memo.get_guardrails(property_id),
        "source_market_mix":  source_market.get_mix(property_id, days=90)
    }
    db.execute("INSERT INTO state_snapshots ...", snapshot_id, property_id,
               ts, **state)
    return snapshot_id
```

Snapshots are eager and immutable. Storage cost at 30 properties × ~30 decisions/day × ~50KB/snapshot is ~45MB/month. Trivial.

## audit_log_decision endpoint

Every Lyzr agent calls this as the final tool before returning.

```
POST /audit/log_decision

Request:
{
  "decision_id":        "<uuid>",        # generated by agent
  "parent_decision_id": "<uuid>",        # from upstream agent in chain
  "property_id":        "<uuid>",
  "agent_name":         "priceguard",
  "agent_version":      "v3.0",
  "prompt_hash":        "<sha256>",
  "model":              "claude-sonnet-4.6",
  "temperature":        0.0,
  "snapshot_id":        "<uuid>",        # links to state_snapshots
  "inputs":             {...},
  "outputs":            {...},
  "tool_calls":         [{...}],
  "duration_ms":        2451,
  "trigger":            "live"
}

Response:
{
  "decision_id":        "<uuid>",
  "status":             "logged"
}
```

Failure mode: if the agent forgets to log, the response is rejected by Lyzr's output schema validator (it requires `audit_decision_id` in every agent's structured output). This forces the audit habit at the prompt level.

## audit_replay endpoint

Re-invokes a Lyzr agent against historical state, optionally with overrides.

```
POST /audit/replay

Request:
{
  "decision_id":        "<uuid>",
  "overrides": {
    "agent_version":    "v3.1",          # try a new prompt
    "model":            "claude-sonnet-4.7",
    "snapshot_overrides": {
      "market_context.regime.regime_score": 0.65
    }
  },
  "mode":               "shadow" | "backtest" | "sandbox"
}

Response:
{
  "replay_decision_id": "<uuid>",
  "original": {
    "outputs":          {...},
    "outcome":          {...}             # if known
  },
  "replayed": {
    "outputs":          {...},
    "predicted_outcome": {                # via elasticity model
      "p_book":           0.74,
      "expected_revpar":  888
    }
  },
  "diff": {
    "price_delta_pct":    0.08,
    "expected_revpar_delta": 23
  }
}
```

Modes:
- `shadow`: replay against original snapshot, return diff. Original outcome is reference.
- `backtest`: same but score the new output via elasticity model and return predicted outcome.
- `sandbox`: do not write a row, just return the diff for ad-hoc exploration.

## Outcome capture

Hostaway webhook listener fills `decision_outcomes` when:
- A new reservation lands (booked)
- A reservation cancels
- A night passes without booking (unbooked)
- An owner manually overrides a price (overridden)

```python
@webhook.post("/hostaway/reservation_created")
def on_reservation(event):
    res = event.data
    affected_nights = generate_nights(res.check_in, res.check_out)
    for night in affected_nights:
        decision = find_decision_for_property_night(res.property_id, night)
        if decision:
            insert_outcome(decision_id=decision.decision_id,
                           target_date=night,
                           outcome_type="booked",
                           realized_price=res.nightly_rate,
                           realized_at=res.created_at,
                           channel=res.channel,
                           los_nights=res.nights,
                           guest_country=res.guest_country)
```

Nightly batch fills "unbooked" outcomes for nights that passed without a reservation match.

## Outcome semantics

`decision_outcomes.outcome_type`:
- `booked`: the night was sold to a guest
- `unbooked`: the night passed and was never booked
- `cancelled`: the night was booked then cancelled (counted separately for elasticity training)
- `overridden`: owner or RM manually changed the price; record the override but flag for separate analysis

## Storage projections

```
Volume               30 properties   100 properties   500 properties
─────────────────────────────────────────────────────────────────────
Decisions/day        ~500            ~1,700           ~8,500
Snapshots/day        ~500            ~1,700           ~8,500
Outcomes/day         ~30             ~100             ~500
Comp obs/day         ~500            ~1,500           ~7,500

Daily storage        ~50 MB          ~170 MB          ~850 MB
Annual storage       ~18 GB          ~62 GB           ~310 GB
```

At 500 properties consider partitioning `agent_decisions` and `comp_observations` by month, or move to TimescaleDB hypertables.

## Backups and retention

- Audit log: keep indefinitely (legal evidence, customer audit rights)
- Snapshots: keep 24 months minimum, archive older to S3 cold storage
- Comp observations: keep 12 months hot, archive older
- Outcomes: keep indefinitely

Daily logical backup of the audit + outcomes tables. Restore-test quarterly.

## Privacy and security

- `inputs` and `tool_calls` JSONB fields may contain `org_id`, `listing_id`, `apiKey`. Apply row-level security so only the owning org can read.
- Customer audit endpoint surfaces sanitized views (no API keys, no internal IDs).
- The original v2 security rule "never expose internal IDs to user" still applies. Sanitization layer between DB and customer-facing API.

## Observability

Instrument:
- Decision write rate (target: ~500/day at 30 properties, alert if drops below 200)
- Snapshot write rate (should match decision rate within 1%)
- Outcome fill rate (rolling 30-day completion %, target >95%)
- Replay endpoint p95 latency (target <2s)
- Backtest harness completion time (target <2 hours for 24 months × 30 properties)
