PriceOS UI Replica and Detailed Client Operating Guide

This HTML file is designed to help a client understand what the current PriceOS product looks like, what each page does, where every KPI, graph, table, and subpage gets its values from, and which AI agents or backend flows sit behind the experience.

Scope and Assumptions

This guide uses the current frontend and API files as the source of truth, not older product notes.

Scope Used For This Version

  • The 7 primary pages are assumed to be /dashboard, /pricing, /market, /guest-chat, /properties, /groups, and /analytics.
  • Separate operational sections are included for /onboarding, /settings, and /users.
  • The guide also includes webhook behavior and the agent/tool-call matrix because those are critical in client demos.

Important Repo Truths

  • Current settings are implemented as two tabs: Connections and Organization. Older docs describing four settings subpages are not the active UI in this repo.
  • Some Pricing and Market buttons point to routes that are not present in the current frontend tree. Those are flagged below as partially wired.
  • Most page math is MongoDB-backed and calculated in Next.js route handlers or page loaders.

Collections and Data Domains Reused Across Pages

  • listings for property metadata, base price, floor, ceiling, activation state.
  • inventory_master for day-level calendar status, current price, proposed price, proposal status.
  • reservations for booking count, LOS, revenue, ADR.
  • hostaway_conversations and guest_threads for Inbox and guest support workflows.
  • ops_tickets, benchmarkdatas, marketevents, airbticscaches, jobs, and organizations for operations, market, caching, and admin state.

Subpages and Interactive Regions

  • Overview tab: core KPI cards, bar and pie charts, occupancy health, action queue, AI signals, performance matrix.
  • Database tab: sync visibility, record counts, and data freshness cues from /api/sync/status.
  • Calendar tab: 30-day portfolio view assembled from each property's calendarDays and reservation overlays.

Primary Render Path

  • Server page loader reads Listing, InventoryMaster, and Reservation.
  • It converts those into propertiesWithMetrics before hydrating OverviewClient.
  • The client then derives filtered KPIs and chart series from the already-hydrated property array.
  • The Sync button is not a Hostaway fetch in this page. It logs a background sync run and reads MongoDB freshness back through /api/sync/status.

Pricing Calendar Subpage

  • Listing selector and month switcher.
  • 365-day fetch through /api/inventory/calendar?listingId=...&days=365.
  • Heat colors reflect day state: booked, blocked, approved, rejected, pushed, or positive/negative proposal movement.
  • Month tooltip shows base price, current price, proposed price, change %, min stay, and day-level reasoning.

Proposals Subpage

  • Status tabs: Pending, Approved, Rejected, Pushed.
  • Filters: property, increase/decrease direction, sort by date / change % / property.
  • Proposal columns: date, property, price, risk, reasoning, action buttons.
  • Generate button starts the pricing engine event stream.

Pricing Rules Subpage

  • Tabs verified in pricing-rules-studio.tsx: Guardrails, Seasons, Lead Time, Gap Logic, LOS Discounts, Date Overrides, Occupancy.
  • These rules define the human-configured pricing envelope that AI and the engine must obey.
  • Occupancy logic includes target occupancy, high occupancy price-up, and low occupancy price-down settings.

What the Client Sees

Current Data Shape

Market KPI and Benchmark Logic

WidgetCalculationSourceImplementation note
Portfolio Occupancy Average of listing occupancyPct across listings loaded into the page. Listing.occupancyPct or 0 fallback. Simple portfolio average, not a weighted booked-night metric.
Avg Nightly Rate Average of listing.avgPrice || listing.price. Listing. Used as a directional market headline rather than a strict ADR audit.
High-Impact Events Count of events where impact === "high". MarketEvent. Window is whatever event set exists in DB, typically next 90 days in UI language.
Total Events Total number of page events loaded for the org. MarketEvent. Raw record count.
Benchmark quartiles Sort same-area listing prices and read p25 / p50 / p75 / p90 by percentile index. /api/agent-tools/benchmark. This is area-based local benchmarking in the current route, not a full external comp scrape.
Verdict UNDERPRICED if price < p25, OVERPRICED if > p90, SLIGHTLY_ABOVE if > p75, otherwise FAIR. Same benchmark route. Clear, client-friendly market positioning label.
Recommended weekend price Math.round(p50 * 1.15). Same benchmark route. Current implementation assumes a 15% weekend premium.

FeatureHow it works nowSourceClient explanation

Separate Flow A: Onboarding

Route: /onboarding. The onboarding wizard is a structured five-step launch flow, not a dashboard page.

Verified current route and save flow
1

Connect

The user enters Hostaway Account ID and API Secret or launches Demo Mode. The wizard calls /api/hostaway/metadata to validate credentials and fetch property names only. A demo fallback can load eight sample Dubai listings.

2

Select

The user selects which listings to activate. This determines which properties are later seeded into the working portfolio and shown across Dashboard, Pricing, Market, and Analytics.

3

Market

The user picks a market template such as Dubai, London, or New York. The market code later drives event and market-intelligence behavior through settings and agent context.

4

Strategy

The user selects conservative, balanced, or aggressive posture and can configure defaults that mirror Pricing Rules Studio concepts: guardrails, seasons, lead time, gap logic, LOS discounts, date overrides, and occupancy logic.

5

Complete

How Webhooks Work

The webhook is the bridge between Hostaway guest messaging and the PriceOS Guest Inbox.

1

Credentials are stored in Settings

The org saves hostawayAccountId and hostawayApiKey. Without these, the webhook cannot be tested or registered.

2

PriceOS derives a public webhook URL

If the app is running locally, the code intentionally falls back to a production base URL so Hostaway has a public endpoint it can reach.

3

Register or update unified webhook

POST /api/hostaway/webhook-manage lists existing unified webhooks, finds a match by exact URL, stored webhook ID, or same path, then creates or updates the record at Hostaway.

4

Hostaway sends message notifications to PriceOS

When guest messages land, Hostaway posts into the configured webhook path. The broader design goal is near-real-time Inbox freshness without polling.

5

PriceOS syncs and stores conversation threads

The verified sync route POST /api/hostaway/conversations/sync?orgId=... fetches conversations and their messages from Hostaway, heals missing listing-to-hostaway mappings where possible, and stores them in hostaway_conversations.

6

Guest Inbox consumes the cached conversations

The UI reads /api/hostaway/conversations/cached, calculates needs-reply state, and lets the Guest Reply Agent draft a response.

Webhook Status Meanings

Status shown in UIMeaning
LiveCredentials exist, authentication succeeds, and the webhook ID is still active or manually confirmed.
Not registeredCredentials are valid, but no active webhook is registered for this org.
Credentials invalidHostaway authentication failed or a saved JWT-style credential expired.
No credentialsSettings are missing Hostaway Account ID or API key.
Client-facing explanation: a webhook is effectively a "push notification channel" from Hostaway to PriceOS. It eliminates the need for constant polling and is what makes the Guest Inbox feel immediate.
